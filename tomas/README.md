# tomas - 입시 상담 예약 서비스

> 학원 입시 상담을 예약하고, 상담사·분석가·관리자가 각 역할에 맞게 처리하는 시스템입니다. 관리자·콘텐츠 기능을 담당했고, 보안 버그 수정, 도메인 모델링, 운영 관리 도구 개발을 했습니다.

## 한눈에

## 1. 보안·인증

### BCrypt 해시 검증 정규식 수정 (SHA-256→BCrypt)

비밀번호 처리를 수정하다가, "이미 암호화된 값인지" 판별하는 가드가 SHA-256 기준인데 시스템은 실제로 BCrypt를 쓰고 있는 불일치를 발견했습니다. 이 상태면 암호화 여부 판단이 틀려 이중 암호화나 검증 실패로 이어집니다. BCrypt 형식 정규식(`^\$2[ayb]\$\d{2}\$[./A-Za-z0-9]{53}$`)으로 판별하도록 고쳤습니다.

### UserDetailsService null 처리 (UsernameNotFoundException)

관리자 아이디가 틀리면 `loadUserByUsername()`이 `null` 사용자로 `getPassword()`를 호출해 NPE가 났습니다. Spring Security의 계약대로 사용자를 찾지 못하면 `UsernameNotFoundException`을 던지도록 바꿨고, Spring Security가 이를 잘못된 자격증명으로 변환해 정상적인 로그인 실패 응답을 냅니다.

### 상담 완료 상태 폼 잠금 (isEditable 단일 메서드)

상담이 완료(`status == 5`)되면 학생이 신청 폼을 더 수정하지 못하게 막아야 했습니다. 편집 가능 여부 판단을 `isEditable()` 한 메서드에 모아 상태 조건을 한 곳에서 관리했습니다.

## 2. JPA 기본값 적용 - @DynamicInsert + columnDefinition

엔티티에 `columnDefinition`으로 DB 기본값을 명시했는데도 기본값이 적용되지 않는 경우가 있었습니다. Hibernate가 `INSERT` 시 모든 컬럼을 포함해 쿼리를 만들면 null이 그대로 들어가 DB 기본값이 무시되기 때문입니다.

`@DynamicInsert`/`@DynamicUpdate`를 붙여 null 필드를 쿼리에서 빼 DB 기본값이 적용되게 하고, Java 필드 기본값(`= 1` 등)도 함께 두어 이중으로 방어했습니다. 또 JPA 엔티티에 잘못 붙어 있던 `@DateTimeFormat`(폼 바인딩용)을 제거하고 영속화 시점은 `@CreationTimestamp`로 분리했습니다. 상태 코드는 `statusText()` 같은 도메인 메서드로 변환을 캡슐화해 컨트롤러·템플릿을 단순하게 유지했습니다.

---

## 3. 공지 게시판 (is_notice/place_order 정렬)

`board`/`post` 도메인 설계부터 REST API·컨트롤러·AJAX JS·Thymeleaf 템플릿까지 한 흐름으로 구현했습니다. 관리자가 공지 순서를 직접 제어해야 해서 등록일 정렬만으로는 부족했습니다. 고정 공지(`is_notice`)와 순서값(`place_order`) 두 컬럼 조합으로 풀고, 공지글과 일반글을 분리 조회했습니다(정렬 의도가 명확해지고 인덱스 활용에도 유리합니다). 콘텐츠 작성에는 TinyMCE WYSIWYG 에디터를 통합하고 한국어 언어팩을 적용했으며, 초기화 로직을 별도 래퍼 파일로 분리해 재사용할 수 있게 했습니다.

---

## 4. tomas_assist (hard delete 운영 대응 관리 도구)

운영 중 목록 화면에서 NullPointerException이 발생해 화면 전체가 깨진 적이 있습니다. 원인은 hard delete로 인한 참조 무결성 위반이었고, 참조하던 데이터가 사라져 NPE가 났습니다.

팀에서 자동 삭제 기능 대신 "고객 요청 → 문제 여부 판단 → 수동 삭제" 순서로 처리하기로 정했고, 삭제는 제가 관리자 역할로 맡았습니다. 매번 DB에 직접 쿼리하는 부담을 줄이려고 Flutter 관리 도구 앱을 별도로 만들었습니다.

```mermaid
flowchart LR
  S["검색<br/>학생명·학부모 전화"] --> L["결과 목록 (페이지네이션)"]
  L --> D["상세 확인"] --> C1{"1차 확인"}
  C1 -- 예 --> API["삭제 API · JWT Bearer"]
  API --> C2["완료 표시 + 정보 클립보드 복사<br/>(운영 기록 추적)"]
```

되돌릴 수 없는 작업이라 2단계 확인을 두었고, 삭제 후에는 학생·학부모 정보를 클립보드로 남겨 나중에 추적할 수 있게 했습니다.

## 잘 됐던 것

- 암호화 여부 체크가 실제 알고리즘과 어긋난 것을 발견해, 제가 작성한 코드가 아니었지만 원인까지 수정했습니다.
- NPE로 화면이 깨지는 문제를 임시 조치로 넘기지 않고, 수동 삭제 절차를 갖춘 별도 앱으로 처리했습니다.

## 아쉬운 것 · 다음엔 다르게

- 상태 코드를 Enum으로 관리했어야 했습니다. `status == 5`(상담완료) 같은 매직 넘버가 코드에 흩어졌습니다. 상태 체계는 Enum/상수로 묶어야 의미가 드러나고 변경 추적이 쉽습니다.
- 관리 도구의 토큰을 하드코딩했습니다. `tomas_assist`에서 JWT를 상수로 두어 만료 시 재배포가 필요한 구조였습니다. 로그인 → 저장(secure storage) → 갱신 흐름으로 구현했어야 합니다.
- 초기에는 전체 도메인 흐름 파악이 부족했습니다. 맡은 기능 중심으로 빠르게 처리하느라 전체 구조를 충분히 보지 못한 채 작업한 부분이 있었습니다.
