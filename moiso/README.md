## 대표 작업

### JPA dirty checking으로 인한 복호화 값 재저장 차단 (detach/flush 순서)

조회 과정에서 DB 값을 복호화해서 반환하는 로직을 구현하면서 운영 중 두 가지 문제가 발생했습니다. 별도의 UPDATE가 없었는데 암호화 컬럼에 평문이 저장되는 문제와, 이미 복호화된 값을 다시 복호화하면서 예외가 발생하는 문제가 있었습니다.

원인은 JPA 엔티티의 영속 상태를 제대로 고려하지 않은 것이었습니다. save() 이후 엔티티는 영속성 컨텍스트에서 관리되고 있었고, 복호화한 값을 엔티티에 set하면서 변경 감지가 발생했습니다. 트랜잭션 커밋 시점에 dirty checking으로 변경된 값이 UPDATE되어 평문이 DB에 저장됐습니다.

당시에는 save() → flush() → detach() → 복호화 순서로 변경하고, 트랜잭션 범위도 다시 정리했습니다. 특히 detach() 전에 엔티티 값을 변경하면 안 된다는 점을 기준으로 수정했습니다.

지금 다시 설계한다면 엔티티 자체를 반환하지 않고 DTO로 변환하는 과정에서 복호화하겠습니다. 영속 상태의 엔티티를 조회용 데이터로 직접 가공하는 것 자체가 문제의 원인이었기 때문입니다.

```mermaid
flowchart TB
  subgraph wrong ["위험 — 평문이 DB로"]
    W1["save() — managed"] --> W2["복호화 값 set"] --> W3["커밋 시 dirty checking<br/>→ 평문 UPDATE"]
  end
  subgraph right ["안전한 순서"]
    R1["암호화 → save"] --> R2["flush"] --> R3["detach"] --> R4["복호화 → 반환"]
  end
  W3 -. 순서 교정 .-> R1
```

### 첨부파일 Base64→AES 점진 전환 (매직패킷 포맷 판별)

운영 중인 상태에서 수천 건의 파일을 Base64 방식에서 AES/CBC 방식으로 전환해야 했습니다. 이미 저장된 파일이 많아서 전체 파일을 한 번에 변환하는 방식은 운영 부담이 컸습니다.

그래서 기존 파일과 신규 파일을 일정 기간 함께 처리할 수 있도록 포맷을 구분하는 방식을 적용했습니다. 파일 앞부분에 4바이트 매직 값을 두고, 해당 값이 있으면 AES 파일로 판단하고 없으면 기존 Base64 파일로 처리했습니다. 파일 앞부분만 확인하면 포맷을 구분할 수 있어서 별도의 DB 컬럼을 추가하지 않아도 됐습니다.

암호화 과정은 CipherOutputStream과 8KB 버퍼를 사용해 스트리밍으로 처리했습니다. 이전에 엑셀 처리에서 대용량 데이터를 한 번에 메모리에 올렸다가 OOM이 발생했던 경험이 있어서, 파일 암호화에서도 전체 데이터를 메모리에 적재하지 않는 방식으로 구현했습니다.

IV는 파일마다 랜덤으로 생성해 사용했습니다. 결과적으로 기존 파일을 일괄 변환하지 않고도 기존 포맷과 신규 포맷을 함께 처리하면서 점진적으로 전환할 수 있었습니다.

```mermaid
flowchart LR
  M["매직패킷 4B<br/>0xDEADBEEF"] --> IV["랜덤 IV 16B"] --> C["AES/CBC 암호문"]
```

### 주민번호 평문 메모리 잔존 제거 (가변 버퍼 + 즉시 RSA)

외부 보안 진단에서 회원가입 과정의 주민번호가 메모리에 평문으로 남아 있는 문제가 발견됐습니다. Frida와 fridump3로 메모리를 덤프해보니 입력한 주민번호가 그대로 확인됐습니다.

처음에는 사용이 끝난 뒤 변수를 null로 변경하면 해결될 것으로 생각했습니다. 하지만 Dart의 String은 immutable이라 기존 문자열 데이터를 직접 덮어쓸 수 없었고, 변수를 제거하더라도 해당 메모리가 GC 전까지 남아 있을 수 있었습니다. 단순히 변수를 삭제하는 방식으로는 해결할 수 없는 문제였습니다.

입력 방식부터 변경했습니다. 주민번호를 String으로 유지하지 않고 List<int> 형태의 가변 버퍼로 받아 처리하고, 사용이 끝난 즉시 fillRange(0, len, 0)으로 버퍼를 0으로 덮어썼습니다. 또한 입력 직후 RSA로 암호화하고 이후에는 암호문만 서버로 전송하도록 흐름을 변경했습니다. 공개키도 매 암호화 직전에 서버에서 받아 사용했습니다.

수정 후 동일한 방식으로 메모리 덤프를 진행했고, 재진단에서 해당 항목이 조치된 것을 확인했습니다.

```mermaid
sequenceDiagram
  participant U as 사용자 입력
  participant A as 앱(Flutter)
  participant S as API 서버
  U->>A: 주민번호 입력 (가변 버퍼, 사용 후 즉시 0으로 덮어쓰기)
  A->>S: 공개키 요청
  S-->>A: 공개키
  A->>A: 입력 직후 RSA 암호화
  A->>S: 암호문만 전송
  S->>S: 복호화·검증
```

### 근무상황표 조회 N+1 제거 (일괄 로드 + 3중 Map 인덱싱)

근무상황표를 한 달 범위로 조회할 때 응답 시간이 10초를 넘는 문제가 있었습니다. 처음에는 쿼리 자체가 느린 문제라고 생각했지만, 확인해보니 쿼리 하나의 실행 시간이 아니라 인원과 날짜가 늘어날수록 조회 쿼리가 반복해서 실행되는 N+1 문제가 원인이었습니다.

기존처럼 각각의 쿼리에 인덱스를 추가해서 실행 시간을 줄이는 대신, 문제를 쿼리 실행 횟수 자체를 줄이는 방향으로 잡았습니다.

전체 근무 로그를 한 번에 조회한 뒤 Map<teacherIdx, Map<날짜, Map<type, Log>>> 구조로 메모리에 인덱싱했습니다. 이후 필요한 로그는 반복문에서 Map을 조회해 바로 가져오도록 변경해 불필요한 DB 조회를 없앴습니다.

조회 데이터가 많아지는 문제는 날짜와 교사를 기준으로 2단계 페이징을 적용했습니다. 그 결과 기존 10초 이상 걸리던 조회를 0.5초 이내로 줄였습니다.

```mermaid
flowchart TB
  subgraph before ["이전 — N+1"]
    L1["선생님 × 날짜 루프"] --> Q1["로그 조회"] --> Q2["로그 조회"] --> Q3["... 수백 쿼리"]
  end
  subgraph after ["이후 — 일괄 로드 + 인덱싱"]
    B1["1회 일괄 로드"] --> B2["3중 Map 인덱싱"] --> B3["루프 내 O(1)"]
  end
  Q3 -. 재설계 .-> B1
```

### 전체 엔드포인트 역할 기반 인가 일괄 적용

로그인 여부인 isLogin만 확인하고 요청을 처리하는 REST 엔드포인트가 많았습니다. 로그인한 사용자라고 해서 모든 기능에 접근할 수 있는 것은 아닌데, 역할에 따른 인가 처리가 빠져 있었습니다.

문제를 확인한 뒤 전체 REST 엔드포인트에 sessionUser.isLoginRole(url)을 적용해 사용자 역할에 따라 접근 권한을 검사하도록 수정했습니다.

다만 URL 문자열을 기준으로 권한을 판단하는 방식이라 URL이 변경되면 권한 로직도 함께 수정해야 하는 한계가 있었습니다. 지금 다시 설계한다면 @PreAuthorize를 사용해 메서드 단위로 권한을 관리했을 것 같습니다.

이 경험을 통해 인가는 인증이 끝난 뒤 별도로 붙이는 작업이 아니라, 기능을 설계할 때부터 접근 권한까지 같이 정의해야 한다는 점을 배웠습니다.

### RSA 키 생성 @PostConstruct 싱글톤화

주민번호 RSA 암호화 초기 구현에서 요청이 들어올 때마다 키쌍을 생성하고 있었습니다. RSA 키 생성은 비용이 큰 작업이라 요청마다 수행할 필요가 없다고 판단했고, @PostConstruct에서 서버 시작 시 한 번만 생성하도록 RsaKeyProvider를 만들었습니다. 앱에서는 /user/get/pubkey를 호출해 공개키를 받아 암호화하도록 했습니다.

다만 서버가 재시작되면 키가 새로 생성되기 때문에 기존 공개키를 가지고 있던 요청이 복호화되지 않을 수 있습니다. 지금 다시 설계한다면 kid를 사용해 키 버전을 구분하고, 키를 교체하는 방식까지 고려했을 것 같습니다.

### 로컬 SQLite AES-256 암호화 (기기별 키 관리)

앱에서 민감정보를 SQLite에 저장하고 있어 기기 분실이나 루팅 시 데이터가 노출될 가능성이 있었습니다. SQLCipher를 적용해 SQLite 데이터베이스 자체를 AES-256으로 암호화했습니다.

여기서 가장 신경 쓴 부분은 암호화 키였습니다. 모든 기기에서 같은 키를 사용하면 앱에서 키가 유출됐을 때 모든 기기의 데이터베이스를 복호화할 수 있기 때문에, 기기마다 별도의 랜덤 키를 생성했습니다. 키는 iOS Keychain과 Android EncryptedSharedPreferences에 저장했습니다.

기존에 저장되어 있던 평문 데이터베이스는 앱 최초 실행 시 암호화된 데이터베이스로 옮기도록 마이그레이션했습니다.

### 개인정보 최소 전송 (encRrn만, 로그 평문 제거)

API 요청에 평문 주민번호가 포함되는 구간이 있었습니다. 평문이 네트워크나 서버 로그에 남을 가능성을 줄이기 위해 일반 요청에서는 rrn 대신 encRrn만 전달하도록 변경했습니다.

평문 주민번호가 실제로 필요한 기능은 getRrn()으로 분리했고, 디버그 과정에서 주민번호가 로그에 출력되던 코드도 함께 제거했습니다.

### 첨부파일 접근 제어 (target→role 선언적 매핑)

첨부파일은 기능마다 접근할 수 있는 역할이 달랐습니다. 그래서 Attach.target을 기준으로 접근 가능한 역할을 static final 맵으로 정의하고, 첨부파일 조회 시 공통으로 권한을 확인하도록 했습니다.

엑셀 파일은 일반 첨부파일과 달리 생성한 관리자(adminIdx) 또는 도청 ADMIN만 접근할 수 있도록 별도로 검사했습니다.

단순히 역할만 확인하는 것이 아니라 첨부파일의 대상과 현재 사용자의 관계까지 확인해야 하는 구조였기 때문에 @PreAuthorize만으로 처리하기보다는 도메인 데이터를 기준으로 권한을 검사하도록 구현했습니다.

### 로그인 비밀번호 RSA (Security 필터 전처리)

로그인 비밀번호를 평문으로 전송하지 않도록 RSA 암호화를 적용했습니다. 프론트에서 서버의 공개키를 받아 JSEncrypt로 비밀번호를 암호화하고, 서버에서는 PasswordPreprocessingFilter에서 복호화하도록 했습니다.

기존 로그인 로직과 BCrypt 처리는 그대로 유지하기 위해 인증 필터 앞에서 요청을 가로채 비밀번호를 복호화한 뒤 HttpServletRequestWrapper로 요청을 교체했습니다. 기존 인증 로직을 크게 수정하지 않고 보안 요구사항을 적용한 방식입니다.

### 연간 시큐어코딩 진단 조치 (예외 세분화·XSS·로깅)

매년 진행되는 보안 진단에서 발견된 항목들을 운영 서비스에 반영했습니다.

XSS 입력 필터를 추가하고, catch(Exception)으로 뭉뚱그려 처리하던 예외를 구체적인 예외로 나눴습니다. printStackTrace()는 로거로 변경하고, I/O 처리는 try-with-resources를 사용하도록 수정했습니다.

또한 권한 확인 없이 userIdx만 전달받아 동작하던 알림 API도 삭제했습니다.

운영 중인 서비스라 한 번에 많은 부분을 변경하기보다는 문제가 된 범위만 수정하고 기존 기능에 영향이 없는지 확인하면서 적용했습니다.

### 집계 쿼리 인덱스 최적화 (컬럼 함수 제거)

연도 조건을 별도 컬럼인 create_year = :year로 변경하고 불필요한 LIKE 조건을 제거했습니다. 조회 빈도가 낮고 무거운 차트는 처음부터 조회하지 않고 사용자가 선택했을 때 조회하도록 변경했습니다.
