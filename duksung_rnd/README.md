# duksung_rnd - 덕성여대 산학협력단 포털

> 교수·연구자의 산학협력 실적을 등록·심사하고 외부 연계 시스템에 제공하는 산학협력단 포털입니다. 프론트엔드 구현과 백엔드 개발을 맡아 운영·고도화했습니다(디자인 제외).

## 한눈에

| 항목 | 내용 |
|---|---|
| 기간 | 2024.03 ~ 2025.08 |
| 역할 | 팀(3인), 프론트엔드 구현·백엔드 개발 |
| 스택 | Java · Spring Boot · Spring Security · JPA · Thymeleaf · MySQL · GitLab |
| 커밋 | 103 (본인 기준) |
| 도메인 | 산학협력 실적, 사업공모 신청·심사, 가족기업, 공용장비 신청, 재직자 교육, QR 인증, 권한 관리 |

별도의 Oracle 연계 API `duksung_api`도 초기 구성했습니다. 주요 작업은 외부 시스템 연계(뷰 테이블 + 코드 변환 계층), 접근제어(IDOR) 패치, 산학실적 심사 워크플로우입니다.

---

## 1. 외부 시스템 연계 - 뷰 테이블 + 코드 변환 계층

산학협력 실적을 외부 연계 시스템에 제공해야 했는데, 외부가 기대하는 컬럼 명세(`ACHIEV_CODE`, `EVAL_CODE`, `CONT_1~15` 등)가 내부 도메인 구조와 달랐습니다. 게다가 그 코드값은 외부 정책에 따라 언제든 바뀔 수 있었습니다.

내부 도메인을 외부 스펙에 직접 맞추면 외부가 바뀔 때마다 도메인·쿼리가 흔들립니다. 그래서 둘 사이에 변환 계층을 두었습니다. 제공 전용 뷰 테이블(`vw_rrm_coopr_achv`)을 따로 설계하고, 내부 코드와 외부 코드의 매핑을 `code_convert` 테이블과 `common` 테이블의 JSON 코드맵(`CONT_CODE_CONVERT`)으로 관리했습니다. 변환은 런타임에 이 매핑을 읽어 처리하므로 **코드값이 바뀌어도 소스 수정과 재배포 없이 DB만 고치면 됐습니다.**

```mermaid
flowchart LR
  R["내부 도메인<br/>BusinessResult"] --> CV["코드 변환<br/>code_convert + CONT_CODE_CONVERT(JSON)"]
  CV --> VW[("vw_rrm_coopr_achv<br/>제공 전용 뷰 테이블")]
  VW --> EXT["외부 연계 시스템"]
```

지식재산권처럼 입력 항목이 많은 카테고리는 `CONT_1~15` 필드 매핑이 복잡했습니다. 하드코딩 문자열이던 매핑을 `common` 테이블의 JSON을 읽어 중첩 `Map`으로 파싱·변환하도록 바꿔, 카테고리마다 다른 구조를 코드 분기 대신 데이터로 처리했습니다.

뷰 테이블에는 최종 승인된 실적만 담아야 했습니다. 심사 저장 시 `status2`가 300(최종 승인)이 아니면 뷰 테이블에서 레코드를 삭제하는 이벤트 동기화로, 두 테이블의 일관성을 상태 변경 시점에 유지했습니다.

```mermaid
flowchart TD
  E["심사 상태 변경"] --> Q{"status2 == 300?<br/>(최종 승인)"}
  Q -- 예 --> KEEP["뷰 테이블 유지 · status=3 자동 전환"]
  Q -- 아니오 --> DEL["뷰 테이블에서 삭제"]
```

## 2. IDOR(URL idx 변조) 소유권 검증

URL의 `idx` 파라미터만 바꾸면 다른 사람의 공용장비 신청·사업공모 신청·인증서를 열람할 수 있는 취약점을 다수 발견했습니다. 인증(로그인)은 있었지만 인가(소유권 검증)가 빠져 있었습니다.

같은 패턴을 공용장비(`MypageRentController`), 사업공모(`MypageBusiness/ResultController`), 접수 성공·기간 만료(`BizController`), 인증서·협약서 출력(`CoopController`) 순으로 적용해, 세션 사용자와 데이터 소유자를 대조하고 불일치 시 차단했습니다. 열람만으로도 민감정보가 노출되므로 출력·다운로드 엔드포인트에도 적용했습니다. SSO 로그인(`DuksungSsoAuthenticationProvider`)에는 이메일 중복 가입 방지도 함께 넣었습니다.

접수 기간 만료 같은 비즈니스 규칙과 보안 검사(IDOR)를 컨트롤러에서 함께 처리한 점은 아쉽습니다. 규칙은 서비스에서 예외로 처리하고 컨트롤러는 redirect만 맡는 구조가 더 적절했습니다.

## 3. 산학실적 심사 워크플로우 (상태 캡슐화 + 이력 추적)

심사 상태 코드(`status` 1·2·3·9 / `status2` 100·200·300)가 정수로 흩어져 있었고, 같은 상태를 관리자에게는 단계별로 상세히, 교수에게는 "심사중" 하나로 보여줘야 했습니다. 변환 로직을 뷰·컨트롤러에 두지 않고 `status2TextToUser()`, `status2BadgeClassTextToUser()` 같은 도메인 메서드로 캡슐화해, 코드값이 바뀌어도 한 곳만 고치면 되게 했습니다.

심사 결과를 수정할 때마다 누가·언제·어떤 상태로 바꿨는지를 `BusinessEvaluation`에 기록했습니다(별도 audit 테이블 대신 평가 테이블 재사용). `status2`가 300에 도달하면 `status`를 3으로 자동 전환해 흐름을 닫았습니다.

승인점수가 "미정" 같은 비숫자로 들어오는 경우가 있어서, `Optional`과 정규식으로 null·빈값·비숫자를 거른 뒤 `BigDecimal`로 안전하게 변환했습니다.

## 그 외 작업

<details>
<summary><b>데이터 정합성 · 운영 안정성</b> (탈퇴 이름 스냅샷 · 장비명 검색 · 서버 다운 감지 도구)</summary>

### 탈퇴 교수 이름 유실 (userName 스냅샷 컬럼)

실적 목록·상세에서 신청자 이름을 `user` 조인으로 가져왔는데, 교수가 탈퇴하면 이름이 사라졌습니다. `businessresult`에 `userName` 컬럼을 추가해 등록·수정 시점의 이름을 스냅샷으로 저장하고, 이후 표시는 조인 대신 그 컬럼에서 읽도록 바꿨습니다.

### 장비명 검색 추가 (countQuery 정합성 유지)

공용장비 검색이 신청자 이름만 대상이라 관리자가 장비명으로 찾을 수 없었습니다. `equipmentapply`-`equipment` JOIN으로 장비명까지 검색 대상에 넣고, countQuery도 같은 조건으로 수정해 총 페이지 수가 어긋나지 않게 했습니다.

### 서버 다운 감지 도구 (asnet_dashboard)

운영 윈도우 서버가 강제 업데이트 후 재부팅되며 주기적으로 다운됐습니다. 다운을 먼저 인지하려고, 사내 여러 서버의 백업 반복 업무와 묶어 SSH 백업과 다운 감지 알림을 통합한 별도 도구([asnet_dashboard](../asnet_dashboard/))를 자발적으로 만들었습니다(덕성여대 포함 9개 사이트 감시). 다운을 막는 도구는 아니어서, 근본적으로는 리눅스 서버 교체로 해결됐습니다.

</details>

## 잘 됐던 것

- 뷰 테이블, 코드 매핑, 상태 동기화까지 외부 연계 구조를 설계부터 구현까지 맡았습니다.
- IDOR를 한 곳에서 막고 끝내지 않고, 같은 패턴을 다른 도메인에서도 찾아 차단했습니다.

## 아쉬운 것 · 다음엔 다르게

- 상태 코드를 Enum으로 관리했어야 했습니다. `status`·`status2`가 정수로 흩어져 대소문자·값 불일치 버그와 가독성 저하를 낳았습니다. Enum으로 묶고 조합 매트릭스를 문서로 남겼다면 인수인계 비용도 줄었을 것입니다.
- 삭제를 GET으로 구현한 곳이 있었습니다. `GET /delete/{idx}`는 HTTP 시맨틱에 맞지 않고 CSRF·prefetch에 취약하므로 `DELETE`/`POST`로 해야 합니다.
- 레거시 직렬화 구조를 초기에 리팩터링했어야 했습니다.
- `ObjectMapper`를 매 호출마다 생성했습니다. thread-safe이고 재사용할 수 있으므로 `@Bean`이나 `static final`로 공유했어야 합니다.
